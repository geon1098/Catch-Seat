# 같은 좌석을 100명이 동시에 예약하면 1명만 성공하는지 검증하는 테스트

> 대상: Java/Spring 을 처음 배우는 사람도 이해할 수 있도록 풀어 쓴 설명서.
> 파일 위치: [backend/src/test/java/com/seat/backend/reservation/ReservationConcurrencyTest.java](src/test/java/com/seat/backend/reservation/ReservationConcurrencyTest.java)

---

## 1. 이 테스트가 풀려고 하는 문제

콘서트 티켓팅을 상상해 보자. **A1 좌석은 단 하나뿐**인데, 같은 1초 안에 **100명이 동시에 "A1 잡아줘!" 버튼을 누르면** 어떻게 될까?

- 잘못 만든 시스템: 100명 중 **여러 명**에게 "예약 성공!" 응답을 줘버린다 → **이중 예약 사고**.
- 잘 만든 시스템: 100명 중 **딱 1명**에게만 성공을 주고, 나머지 99명에게는 "이미 다른 분이 잡았어요" 라고 응답한다.

이 테스트는 **"우리 코드는 잘 만든 시스템이다"** 를 증명하는 자동화된 검증이다.

실행 결과 기댓값:

```
success=1, fail=99
```

## 2. 한 줄 한 줄 무엇을 하는지

### 2-1. `@SpringBootTest` 가 뭐길래

```java
@SpringBootTest
class ReservationConcurrencyTest { ... }
```

- `@SpringBootTest` 는 "이 테스트는 **진짜 스프링 부트 앱을 띄워서** 실행해" 라는 의미.
- 단순한 단위 테스트가 아니라, 실제 DB(MySQL) 에 연결해서 SQL 까지 흐르게 하는 **통합 테스트**.
- 동시성 버그는 가짜 객체(Mock)로는 절대 못 잡는다 — DB 의 진짜 락 동작이 필요하기 때문.

### 2-2. `@BeforeEach` — 테스트 시작 전 무대 세팅

```java
@BeforeEach
@Transactional
void setUp() { ... }
```

매번 테스트가 돌기 전에:

1. **이전에 만들어진 예약을 다 지운다** — 그래야 매번 깨끗한 상태에서 시작한다.
2. **좌석 1번을 다시 `AVAILABLE`(예약 가능)로 되돌린다** — 직전 테스트가 좌석을 `HOLD` 로 바꿨을 수 있으니까.
3. **테스트용 유저 1명을 만들어 둔다** — 예약 INSERT 시 외래키(FK) 제약을 만족시키기 위해 필요.

> "왜 유저 1명만 있어도 되지? 100명이 동시에 누르는 거 아니었나?" 라고 의심할 수 있다.
> → 어차피 100개 스레드 중 **DB 락을 차지하는 건 1개**뿐이고, **INSERT 까지 가는 것도 1개**뿐이다. 나머지 99개는 좌석 상태가 이미 `HOLD` 라는 걸 보고 즉시 예외를 던지며 끝난다. 그래서 유저는 1명만 있어도 충분.

### 2-3. 본 테스트 — 100명 동시 클릭 흉내내기

```java
ExecutorService pool = Executors.newFixedThreadPool(32);
CountDownLatch latch = new CountDownLatch(THREADS); // THREADS = 100
AtomicInteger success = new AtomicInteger();
AtomicInteger fail    = new AtomicInteger();
```

처음 보면 외계어 같으니 비유로 풀어보자.

| 코드 | 비유 |
|---|---|
| `ExecutorService pool = ...newFixedThreadPool(32)` | **알바생 32명**을 고용한다. 이 알바생들이 "예약 시도" 작업을 나눠서 처리한다. |
| `CountDownLatch latch = new CountDownLatch(100)` | **체크리스트 100칸**짜리. 작업 하나 끝날 때마다 한 칸씩 지운다. 0칸이 되면 메인 스레드가 깨어난다. |
| `AtomicInteger success` | **성공 카운터**. 여러 스레드가 동시에 +1 해도 값이 망가지지 않는 안전한 정수. |
| `AtomicInteger fail` | **실패 카운터**. 같은 이유로 안전한 정수. |

> ※ 32명한테 100개 작업을 시키는 이유: 동시에 32개씩 처리되고, 끝나는 사람부터 다음 작업을 받아간다. 그래야 한 좌석에 **진짜로 동시에** 부하가 걸린다.

```java
for (int i = 0; i < THREADS; i++) {
    pool.submit(() -> {
        try {
            reservationService.reserveWithPessimistic(testUserId, SEAT_ID);
            success.incrementAndGet();
        } catch (Exception e) {
            fail.incrementAndGet();
        } finally {
            latch.countDown();
        }
    });
}
```

- **알바생들에게 작업 100개를 던져준다** (`pool.submit`).
- 각 작업은 `reserveWithPessimistic(...)` 을 호출한다 — 이게 진짜 예약 로직.
- 예외 없이 끝나면 → 성공 카운터 +1.
- 예외가 터지면 → 실패 카운터 +1.
- 끝나면 체크리스트 한 칸 지움 (`latch.countDown()`).

```java
latch.await(30, TimeUnit.SECONDS);
pool.shutdown();
```

- 메인 스레드는 **체크리스트가 다 지워질 때까지 (최대 30초) 기다린다**.
- 그 후 알바생 인력(스레드 풀)을 해산.

### 2-4. 결과 검증

```java
assertThat(success.get()).isEqualTo(1);
assertThat(fail.get()).isEqualTo(99);
```

- 성공이 정확히 1, 실패가 정확히 99 여야 한다. 그 외엔 **테스트가 빨갛게 깨진다**.
- 추가로, DB 에 실제로 남은 예약도 1건뿐임을 검증.

## 3. 왜 1명만 성공하는가? — 비관적 락 (Pessimistic Lock) 의 마법

핵심은 `reserveWithPessimistic` 이 호출하는 **`SELECT ... FOR UPDATE`** SQL 한 줄이다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from Seat s where s.id = :id")
Optional<Seat> findByIdForUpdate(@Param("id") Long id);
```

이게 만들어내는 SQL 은 대략:

```sql
SELECT * FROM seats WHERE id = 1 FOR UPDATE;
```

**`FOR UPDATE`** 가 붙은 SELECT 를 만나면 MySQL(InnoDB)은 그 행에 **배타적 락(X-Lock)** 을 걸고, **트랜잭션이 끝날 때까지 다른 트랜잭션은 같은 행을 못 읽게 막는다.**

100개의 스레드가 동시에 들어왔을 때 벌어지는 일을 시간 순으로 보면:

```
T1:   SELECT seats id=1 FOR UPDATE   → 락 획득 ✓ → 좌석 상태가 AVAILABLE 인지 확인 → HOLD 로 변경 → 예약 INSERT → COMMIT (락 해제)
T2:   SELECT seats id=1 FOR UPDATE   → 대기...
T3:   SELECT seats id=1 FOR UPDATE   → 대기...
...
T100: SELECT seats id=1 FOR UPDATE   → 대기...

(T1 이 COMMIT 후)

T2:   대기 풀림 → SELECT 결과를 보니 status=HOLD → "어! 이미 누가 잡았네" → SEAT_NOT_AVAILABLE 예외
T3:   대기 풀림 → 마찬가지로 status=HOLD → 예외
...
T100: 마찬가지로 예외
```

결과적으로 T1 만 success +1, T2~T100 은 fail +1 → **`success=1, fail=99`**.

## 4. 락이 없으면 어떻게 깨지나? (비교)

같은 테스트를 `reserveNoLock`(락 없는 버전) 으로 돌려보면:

```
success=7, fail=93   ← 매번 들쭉날쭉. 1보다 큰 값이 나올 수 있음.
```

이유는 **race condition**:

```
T1: SELECT seats id=1     → status=AVAILABLE 로 읽음
T2: SELECT seats id=1     → status=AVAILABLE 로 읽음 (T1 이 아직 UPDATE 전!)
T1: UPDATE status=HOLD    → 성공
T2: UPDATE status=HOLD    → 또 성공! (이미 T1 이 바꿨는지 모름)
→ 같은 좌석에 예약이 2건 INSERT 됨 = 이중 예약 사고
```

DB 의 기본 격리 수준(`READ_COMMITTED`)은 "다른 트랜잭션이 **커밋한** 데이터는 보여준다" 일 뿐, "같은 행을 동시에 못 만지게 막는다" 가 아니다. 그래서 락이 별도로 필요하다.

## 5. 자주 막히는 포인트 — FAQ

### Q1. 테스트가 `seatId=1 좌석이 없습니다` 에러로 시작도 못 한다.
A. MySQL 컨테이너에 [db/init.sql](../db/init.sql) 의 시드 데이터가 들어갔는지 확인. 도커 볼륨이 한 번 만들어진 후엔 init.sql 이 다시 안 돈다 — 컨테이너+볼륨을 통째로 지우고 다시 띄워야 시드가 다시 실행된다.

### Q2. `AtomicInteger` 대신 그냥 `int success = 0` 쓰면 안 되나?
A. 안 된다. `int` 는 여러 스레드가 동시에 `success++` 하면 **값이 깨진다** (예: 100번 +1 했는데 결과가 73). `AtomicInteger.incrementAndGet()` 은 CPU 의 CAS(Compare-And-Swap) 명령어를 써서 동시에 호출돼도 값이 정확하다.

### Q3. `CountDownLatch` 없이 그냥 `Thread.sleep(5000)` 으로 5초 기다리면 안 되나?
A. 가능은 하지만 나쁜 패턴이다. 작업이 1초 만에 끝나면 4초 낭비, 6초 걸리면 결과가 부정확. **"끝났다는 신호"** 를 기반으로 기다리는 게 정석.

### Q4. `latch.await(30, TimeUnit.SECONDS)` — 30초는 어디서 나온 숫자?
A. **데드락 방지용 안전 장치**. 만약 락 로직에 버그가 있어 영영 안 끝나면 테스트가 무한히 멈춘다. 30초가 지나면 강제로 빠져나와 테스트를 실패시켜 알려준다.

### Q5. 100개의 작업인데 알바(스레드)는 32명? 충분한가?
A. 충분하다. **동시성 테스트의 목표는 "한 시점에 여러 스레드가 락을 다툰다"** 를 만드는 것이지, 정확히 100개가 동시에 시작될 필요는 없다. 32개가 동시에 부딪히는 것만으로도 race window 가 충분히 노출된다. 또한 100개 모두 동시에 띄우면 OS 스레드 비용이 커져서 오히려 부정확.

### Q6. 왜 `@Transactional` 이 `setUp()` 에는 있는데 본 테스트 메서드에는 없나?
A. 본 테스트 메서드는 **여러 트랜잭션이 동시에 다투는 상황**을 보고 싶은 것이다. 만약 테스트 메서드 자체에 `@Transactional` 을 붙이면 모든 작업이 하나의 트랜잭션 안에서 일어나서 **락 다툼이 안 일어난다** — 동시성 테스트의 의미가 사라진다. `setUp()` 은 단순히 데이터를 정리하는 거라 트랜잭션 하나로 충분.

## 7. 한 줄 요약

> **"`@Lock(PESSIMISTIC_WRITE)` 한 줄과 `@Transactional` 한 줄로, 100명이 동시에 같은 좌석을 노려도 단 1명만 잡을 수 있다."**

이 테스트는 그 사실을 **자동으로, 매번 빌드할 때마다, 기계적으로** 검증해 준다. 사람이 클릭으로 확인할 수 있는 동시성 버그는 거의 없으니, 이런 테스트가 곧 보험이다.
